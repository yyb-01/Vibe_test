# 변경 집합 비동기 저장 측정

```powershell
./scripts/benchmark-sqlite.ps1 -Async
```

2026-09-14 Windows x64, Zig 0.15.2 `-O2`, SQLite 3.53.4. 기존 [합성 월드](PERFORMANCE.md)와 같은 아이템 이동을 크기별 준비 운동 1회 후 20회 측정했다. 전체 월드 복사·검증·SQLite 체크포인트 쓰기는 worker에서 실행한다. 원본은 [async-delta.csv](../benchmark/async-delta.csv)다.

| 아이템 | 메시지 예산 사용 B | 제출 p50/p95 ms | resolve 최대 호출 p50/p95 ms | 왕복 p50/p95 ms |
|---:|---:|---:|---:|---:|
| 100 | 5,136 | 0.074 / 0.103 | 0.047 / 0.094 | 15.990 / 16.112 |
| 1,000 | 5,136 | 0.060 / 0.115 | 0.040 / 0.182 | 15.971 / 16.127 |
| 10,000 | 5,136 | 0.062 / 0.155 | 0.045 / 0.140 | 63.121 / 64.189 |
| 60,000 | 5,136 | 0.072 / 0.139 | 0.056 / 0.120 | 379.418 / 409.988 |

제출은 `DurableInventory::apply`의 검증·준비·delta 생성·직렬화·접수 시간이다. 메시지 값은 vector capacity와 고정 관리 공간 4,096B를 합친 값이며 전체 메모리 사용량이 아니다. `resolve_peak`는 각 거래에서 가장 오래 걸린 resolve 호출 시간을 모아 계산했다. 왕복에는 DB 처리·호출 스레드 확정·1ms 폴링 대기가 포함된다. 단계별 p50을 합산한 값이 아니다.

매 거래 결과·순번을 검사하고, 정상 종료 후 DB를 다시 acquire해 전체 월드와 최종 순번이 메모리와 일치하는지 확인한다. CSV의 startup/shutdown은 최초 로딩과 최초 종료·백업이며 검증용 재시작 시간은 제외한다. DB는 매번 새 경로를 사용한다.

호출 스레드의 전체 체크포인트 처리는 제거했지만 worker와 SQLite의 O(N) 비용은 남았다. 6만 개에서 요청 제출 0.072ms가 저장 완료 시간이라는 뜻은 아니다. 20인 동시 부하·렌더링·전체 메모리 예산은 미측정이며 OneDrive 아래 개발 경로에서의 단일 실행이다. 다음 단계는 SQLite 변경 행 저장이다.
