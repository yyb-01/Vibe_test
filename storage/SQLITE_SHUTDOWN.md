# 정상 종료와 백업

명세 0.1의 서버는 **방장 PC의 게임 리슨 서버**다. SQLite는 방장 게임 프로세스에 포함된 저장 라이브러리이며 접속용 서버를 만들지 않는다. 참가자는 게임 서버에 명령을 보내고 방장이 검증·판정·저장한다. 방장이 나가면 세션이 끝나며 자동 방장 이전은 초기 범위에 없다. 실제 UE 방 생성/참가는 아직 미구현이다.

명세 E.8의 저장 종료 부분을 `DurableInventory::close()`로 구현했다.

```cpp
auto result = inventory.close();
// Ok: 저장 종료 및 백업 완료. 호스트 종료 절차를 이어갈 수 있다.
// Pending: 저장 결과 미확정. 객체를 유지하고 close()를 재시도한다.
// 그 밖의 오류: 성공으로 표시하지 말고 원인을 해결한 뒤 재시도한다.
```

첫 호출부터 새 `apply()`는 `Busy`로 거절한다. 대기 거래는 DB 결과를 조회해 확정 또는 롤백 여부를 확인하고, 결과를 알 수 없으면 백업·잠금 해제를 하지 않는다. `close()`의 `Ok`는 종료 성공이며 이전 `Pending` 거래의 성공 ACK가 아니다. 거래 결과는 저장된 requestId로 조회/재전송하는 기존 경로에서 확인한다.

SQLite는 일관된 읽기 스냅샷에서 [Backup API](https://www.sqlite.org/backup.html)를 이용해 임시 DB를 만든다. SQLite 무결성 검사와 체크포인트 전체 비교를 통과한 뒤 `world.sqlite3.backups/backup-<20자리 epoch>.sqlite3`로 게시한다. Windows에서는 [MoveFileExW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw)의 `MOVEFILE_WRITE_THROUGH`를 사용한다. 원본 DB/WAL 파일을 직접 복사하거나 삭제하지 않는다.

새 백업 게시 후 정상 백업을 최근 3개로 줄인다. 손상·읽기 불가 백업과 강제 종료가 남긴 임시 파일은 진단용으로 보존하고 3개 한도에서 제외한다. 따라서 폴더 전체 파일 수는 3개보다 많을 수 있다. 생성 실패 시 이전 백업을 삭제하지 않으며, 오래된 백업 삭제가 실패해도 새 백업과 잠금을 유지한다. 재시도는 이미 게시한 백업의 내용부터 확인한다.

정상 종료에는 반드시 `close()`를 호출하고 결과를 확인한다. 소멸자는 강제 종료처럼 자원만 해제하며 자동 백업 성공을 약속하지 않는다. 종료 성공 후 반복 `close()`는 같은 성공을 반환하고 새 백업을 만들지 않는다. 스냅샷은 계속 읽을 수 있지만 새 명령은 받지 않는다.

검증: `./scripts/test-sqlite.ps1`. WAL에 남은 상태/요청 결과의 백업, 5회 종료 후 정상 3개 유지, 백업에서 중복 요청 복구, 손상·임시 파일 보존, 미확정 종료 보류, 백업/삭제 실패 후 재시도와 잠금 유지를 시험한다.

직접 SQLiteStore 연결의 종료 호출은 동기식이며 [AsyncStore](ASYNC.md) 연결에서는 백업·닫기가 worker에서 진행된다. UE 참가자 통지, 비핵심 상태 최종 저장, 기존 월드를 보존하고 별도 lineage로 여는 복원 기능은 후속 항목이다. 실제 전원 차단과 Windows 외 플랫폼은 미검증이다.
