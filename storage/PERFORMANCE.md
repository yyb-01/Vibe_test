# 저장 성능 기준선

```powershell
./scripts/benchmark-sqlite.ps1
./scripts/benchmark-sqlite.ps1 -Items 100,1000 -Samples 10
```

코어와 저장 어댑터를 Zig 0.15.2의 `-O2`로 빌드한다. 실행마다 `.build/benchmarks/<GUID>`에 합성 DB와 `results.csv`를 만든다. 기존 세이브를 사용하지 않는다. CMake에서는 `ASTRA_SQLITE=ON`의 `astra_storage_benchmark`를 Release로 빌드하고 `DB_PATH ITEM_COUNT SAMPLE_COUNT` 인자로 실행한다. DB 부모 폴더는 미리 생성한다.

2026-09-14 Windows x64 워크스페이스에서 측정했다. SQLite 3.53.4, 크기별 준비 운동 1회 후 20회 표본이다. 한 계정이 두 작은 루트 사이로 아이템 하나를 번갈아 이동하고, 나머지 아이템은 루트당 최대 200개씩 다른 루트에 둔다. 표는 중앙값(p50), 단위는 ms다.

| 아이템 수 | 준비 | 체크포인트 생성 | 직렬화·검증 | SQLite save | 메모리 확정 |
|---:|---:|---:|---:|---:|---:|
| 100 | 0.031 | 0.053 | 0.205 | 14.072 | 0.015 |
| 1,000 | 0.032 | 0.418 | 1.645 | 18.939 | 0.016 |
| 10,000 | 0.039 | 4.033 | 16.692 | 74.185 | 0.022 |
| 60,000 | 0.043 | 20.065 | 121.363 | 401.042 | 0.025 |

원본 수치는 [baseline.csv](../benchmark/baseline.csv)에 있다. 각 단계의 p95, 마지막 체크포인트 바이트 수, 최초 acquire와 정상 종료·백업 시간도 기록한다. 60,000개에서 체크포인트는 6,749,104B였고 직렬화·검증 p95는 136.431ms였다.

`sqlite_save`는 SQLiteStore::save 전체로, 내부 직렬화·현재 DB 읽기/검증·트랜잭션·COMMIT을 포함한다. 순수 디스크 flush 시간은 아니다. 별도로 측정한 encode도 save 안에서 다시 실행하므로 두 수치를 더해 총 거래 시간으로 해석하면 안 된다. 마지막 DB 체크포인트가 준비한 결과와 같은지 확인하고 매 거래의 저장/메모리 확정 결과도 검사한다.

이 기준선에서는 루트 단위 준비·확정 비용은 작았지만 전체 월드 복사와 codec 검증 비용은 데이터 크기에 따라 증가했다. 이후 AsyncStore의 거래 메시지를 변경 집합으로 바꿔 호출 스레드의 전체 체크포인트 생성·직렬화를 제거했다. [비동기 측정 결과](ASYNC_PERFORMANCE.md)를 별도로 기록했다. SQLite 변경 행 저장은 남아 있으며 요청 결과·fencing·Unknown 재확인·복구의 원자성을 유지해야 한다.

합성 단일 거래 기준선이며 20인 게임 부하나 비동기 왕복 처리량 측정은 아니다. 경로가 OneDrive 아래인 개발 워크스페이스였으므로 운영 로컬 디스크 지연을 대표하지 않는다. 렌더링 포함 60Hz 예산과 메모리 최대 사용량은 별도 측정이 필요하다.

## 검증 복사 최적화 (2026-09-14)

검증 중 아이템·배치는 읽기만 하고, 파생 집계를 다시 계산할 컨테이너만 복사한다. 부모 경로는 검증 호출마다 컨테이너별로 한 번 계산한다. 깊이 최대 5인 경로의 cycle 검사도 별도 set 대신 기존 경로를 검색한다. 저장 형식·검증 규칙은 유지한다.

동일 크기·20표본·O2의 재측정 [validation-after.csv](../benchmark/validation-after.csv):

| 아이템 | 직렬화·검증 이전 p50 | 이후 p50 | 이후 p95 |
|---:|---:|---:|---:|
| 100 | 0.205 | 0.106 | 0.151 |
| 1,000 | 1.645 | 0.949 | 1.172 |
| 10,000 | 16.692 | 8.622 | 12.520 |
| 60,000 | 121.363 | 68.618 | 88.121 |

단위 ms. 6만 개 직렬화·검증 중앙값은 기준선 대비 43.5% 감소했다. 같은 구현의 [첫 측정](../benchmark/validation-after-first.csv)에서는 79.663ms였다. 첫 측정에는 코어 테스트 빌드가 겹쳐, 재측정은 별도 빌드 없이 실행했다. SQLite save 중앙값은 두 실행에서 724.804/278.333ms로 편차가 커 고정 개선율을 주장하지 않는다. 체크포인트 크기는 기준선과 동일하고 각 실행의 최종 DB 내용 검증은 통과했다. 전체 복사·직렬화의 O(N) 비용은 남으므로 게임 틱 예산 충족을 뜻하지 않는다.
